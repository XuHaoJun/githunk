# githunk v0.1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the review-first Git TUI described by the v0.1 PRD, including working-tree and aggregate branch review, precise patch copy and partial staging, persisted review progress, daily-driver Git operations, remote tracking checkout, and resizable OpenTUI panes.

**Architecture:** Build a Bun/TypeScript monolith with explicit boundaries: pure domain and patch modules, a shell-free Git command adapter, a controller that serializes mutations and refreshes immutable application state, and an OpenTUI view layer. Deliver vertical slices so every task leaves a usable, testable application; use the lazygit submodule only as a behavioral and edge-case reference, never as a runtime dependency.

**Tech Stack:** Bun, strict TypeScript, `@opentui/core` 0.5.6, Git CLI, Bun test, OpenTUI test renderer.

**Spec:** `docs/githunk-prd-v0.1.md`

**Supporting evidence:** `spikes/selection/findings.md`

## Global Constraints

- Pin `@opentui/core` exactly to `0.5.6`; do not reuse the disposable spike as application architecture.
- Pin TypeScript to `5.9.2` to remove the observed TypeScript 7 peer-dependency warning.
- Invoke Git with argument arrays through `Bun.spawn`; never construct a shell command string.
- Every Git invocation, including failures, must produce an inspectable command-log record.
- Preserve the last successful view model when a refresh command fails; show the error and failed command instead of blanking panes.
- Serialize mutating Git commands. Block repeat input until the mutation and its scoped refresh finish.
- Keep the active review target and inferred or selected branch base visible at all times.
- Persist review state below Git metadata, never in the working tree.
- Confirmed clipboard compatibility floor is SSH + zellij. Do not advertise local, SSH-only, or tmux clipboard support until tested.
- Patch selection must use the selectable Main renderable. Adjacent panes and the Command Log must remain non-selectable.
- Partial patch transformations must cover neighboring hunks, context, additions, deletions, mixed changes, renames, new/deleted files, no-final-newline markers, CRLF, Unicode, and paths containing spaces.
- Binary and conflicted files remain inspectable and whole-file stageable where Git permits it; disable line/hunk staging with an explicit reason.
- Destructive actions require a confirmation dialog naming the exact target. Cancellation must execute no command.
- `learn-projects/lazygit` is a read-only reference for behavior and tests. Do not import, copy wholesale, or couple production code to its Go packages.

## Delivery Strategy

Use vertical slices rather than building the whole UI before Git behavior:

1. executable shell and observable Git boundary;
2. working-tree review;
3. complete resizable information architecture;
4. document-aware copy;
5. safe partial staging and discard;
6. review progress;
7. aggregate branch review;
8. history, branches/remotes, commit, stash, and synchronization;
9. compatibility and end-to-end acceptance.

This is preferred over a framework-first shell because partial patch correctness and review-target semantics are the highest product risks. It is preferred over porting lazygit because githunk's review model and TypeScript/OpenTUI stack need smaller, explicit boundaries.
